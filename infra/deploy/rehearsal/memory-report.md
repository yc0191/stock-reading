# 로컬 리허설 메모리 측정

`run-rehearsal.sh all`로 측정했습니다(2026-11-11). 서버 2대는 각각 메모리·스왑 상한 2GB의 Docker 컨테이너(Docker 안의 Docker)이고, 이미지는 `linux/amd64`입니다(에뮬레이션으로 돌렸을 수 있어 실제 서버와 완전히 같지는 않습니다). 시세는 시뮬레이터, 메일은 드라이런, LLM 키는 없음(규칙 기반 리포트)입니다. 외부 호출은 없습니다.

## 한 일

1. 데이터 서버(`data.yml`)와 서비스 서버(`services.yml`)를 띄움.
2. `flyway-migrate`가 market, personal 계정·권한, personal, briefing 순서로 표를 만든 뒤 서비스 5개가 뜸.
3. 가짜 종목·멤버 2명(서로 다른 포트폴리오)을 넣고 수집기·뉴스를 다시 띄움.
4. 수집기 수동 명령(`collect`, `collect-pre-open`, `collect-intraday`, `collect-post-close`, `collect-news`)과 tick(`collect-members`, `daily-briefing-morning`, `daily-briefing-post-close`)을 발행하고 150초 기다림.

## 두 번째 배포(서비스가 도는 중 새 버전 태그로 apply)

운영 배포와 같은 상황입니다. 서비스 5개가 도는 중에 새 버전 태그(`dev2`)로 `up -d`를 해 DB 표 만들기 단계가 다시 돌고 서비스가 새로 만들어지는 약 60초를 1초 안팎 간격(19회)으로 쟀습니다.

- **서비스 서버 전체(Docker 데몬 포함) 최대 1680 MiB**(상한 2048). flyway-migrate 최대 209 MiB(상한 384m 안), 서비스 5개는 각각 첫 기동과 비슷한 값.
- 두 번째 배포 뒤 서비스 5개 모두 실행 중, 재시작 0회, OOM 종료 없음. flyway-migrate는 종료 코드 0, 실행 사용자 `flyway`(root 아님).
- 상한이 없던 때(이전 구성)는 이 순간을 재지 못했습니다. 지금은 상한 384m 안에서 끝나며, 옛·새 서비스가 겹치는 구간에서도 서버 전체는 2048 안에 들었습니다.

## 해석

- 서비스 서버는 2GB 안에 들며 여유는 약 370MiB입니다. **4GB로 올릴 필요는 없지만 여유가 크지 않습니다.** 종목·멤버가 늘거나 브리핑이 LLM·차트를 실제로 돌릴 때(이번에는 키가 없어 규칙 기반) 브리핑 메모리가 커질 수 있어, 첫 실제 운영 때 다시 확인합니다.
- Java 서비스 하나는 힙 160~224MiB 상한인데 컨테이너 사용량은 340~365MiB입니다. 힙 밖(메타스페이스, 코드 캐시, 스레드 스택, JVM 자체)이 약 150MiB이기 때문입니다.
- 측정 때 `notifier` 상한이 360m이어서 사용량 339MiB와 가까워 400m로 올렸고(`NOTIFIER_MEM_LIMIT`), 올린 뒤 다시 쟀습니다(최대 315MiB). 컨테이너 상한 합(1980MiB)은 서버 메모리보다 크지만 실제 사용 합은 1478MiB입니다.
- 5초마다 잰 값이라 순간 최고치는 더 클 수 있습니다.
