# PR 규칙

PR을 만들기 전에 읽습니다.

## PR 생성 전 확인: 문서 동기화

코드·설정과 문서(ADR, README, 가이드)가 서로 맞는지 확인합니다. 어긋나면 같은 PR에서 고치거나 따로 뺍니다.

- 동작·구조·결정이 바뀌었으면 → 해당 ADR에 반영되어 있는지 확인합니다. 없으면 ADR 추가·수정을 제안합니다.
- ADR의 상태가 바뀌었으면 → ADR 인덱스(`docs/adr/README.md`)의 상태와 행이 일치하는지 확인합니다.
- 아키텍처·기술 스택·서비스 구성이 바뀌었으면 → README의 구성도, 기술 스택, 로드맵(체크박스), 문서 링크가 맞는지 확인합니다.
- 실행 명령, 설정 키, 테스트 명령이 바뀌었으면 → `docs/local-development.md`가 맞는지 확인합니다.
- 반대로 문서가 앞서가지 않았는지 확인합니다. 코드에 없는 기능을 "구현됨"으로 쓰지 않습니다.

## 머지 방식

- **Merge commit**으로 합칩니다. 브랜치의 커밋 이력을 그대로 보존하고, Squash와 Rebase는 쓰지 않습니다.

## 제목

- **영어 문장**으로 씁니다. 커밋의 `[keyword] : title` 형식을 쓰지 않습니다.
- 브랜치의 커밋을 모두 확인하고 **전체를 종합해서** 씁니다. 한 커밋의 제목을 그대로 쓰지 않습니다.
- 동사로 시작하는 한 문장이며 마침표는 붙이지 않습니다.
  - 예: `Add project skeleton with MVP services and event contract tests`
- 쉬운 단어로 씁니다. 어려운 단어와 긴 수식은 피합니다.

## 본문

본문은 한글로 작성하고, 아래 템플릿의 섹션을 순서대로 모두 씁니다.

```
## 요약
- 이 PR이 무엇을 하는지 1~3줄

## 변경 내용
- 동작·기능 단위의 변경 내용 (커밋 메시지의 <description>을 종합)

## 변경 파일 요약
- 디렉터리 : 변경 범위와 파일 수
```

- **제목과 본문만 읽고 코드를 보지 않아도 무엇이 바뀌었고 왜 필요했는지 이해되어야 합니다.** 코드 안의 이름이나 사정을 알아야 읽히는 문장은 풀어서 쓰고, 이를 해치지 않는 범위에서 꼭 필요한 말만 짧게 씁니다.
- **변경 파일 요약**은 `git diff --stat`의 실제 결과를 기준으로 하고, 추측하지 않습니다. 새로 추가하거나 삭제한 중요한 파일이 있으면 함께 적습니다.
