# 커밋 메시지 규칙

커밋 메시지를 작성할 때 읽습니다.

커밋 메시지의 목적은 변경된 파일을 하나하나 열어 보지 않아도 메시지만으로 커밋의 전체 내용을 명확하게 파악할 수 있게 하는 것입니다.

## 형식

```
[keyword] : title

<description>
* 대상 : 변경 내용
* 대상 : 변경 내용

<why>
* 이유
* 이유

<risk>
* 주의할 점

<todo>
* 후속 작업
```

- 제목은 `[keyword] : title` 형식이며, `keyword`와 `title`은 **영어**로 씁니다.
  - `title`은 쉬운 단어로 쓴 짧은 문장입니다. 어려운 단어와 긴 수식을 피하고, 읽는 사람이 바로 이해하는 말만 씁니다.
    예: `Lower the call limit to 10`(좋음), `Reconcile divergent rate limiting abstractions`(나쁨)
- 본문(항목 안의 문장)은 한글로 작성합니다. 코드 식별자·파일명·기술 용어는 원문을 유지합니다.
- 각 항목은 `* ` 로 시작하는 줄로 나열합니다.
- `<description>` 과 `<why>` 는 **필수**입니다.
  - `<description>` 은 `* 변경 대상 : 변경 내용` 형식으로, 파일 단위가 아니라 동작·기능 단위로 구체적으로 적습니다.
    예: `* README.md 내용 추가 : 프로젝트 소개, 목표, 서비스 및 토픽 흐름도, 설계 원칙, 기술 스택 ..`
    예: `* 서비스 및 토픽 흐름도 : mermaid 형식 - 가독성 증가`
  - `<why>` 는 왜 이 변경이 필요했는지 적습니다.
- `<risk>` 와 `<todo>` 는 **실제로 있을 때만** 쓰고, 없으면 섹션 제목째 생략합니다. 채우기 위해 억지로 만들지 않습니다.
  - `<risk>`: 영향 범위, 부작용, 호환성 문제처럼 리뷰어가 알아야 할 위험
  - `<todo>`: 이 커밋만으로는 끝나지 않아 후속으로 해야 할 일
- 변경 내용을 추측하지 않고 실제 diff에 근거해 작성합니다.
- **메시지만 읽고 코드를 보지 않아도 무엇이 바뀌었고 왜 필요했는지 이해되어야 합니다.** 코드 안의 이름이나 사정을 알아야 읽히는 문장은 풀어서 씁니다.
- 그 안에서 꼭 필요한 말만 짧고 힘 있게 씁니다. 항목마다 "이 줄을 지워도 코드를 열지 않고 이해되는가"를 묻고, 그렇다면 지웁니다.
  - 파일 이름 나열, 같은 말의 반복, 변명과 수식어를 쓰지 않습니다.
  - 한 커밋에는 한 가지 목적만 담습니다. 목적이 다른 변경은 커밋을 나눕니다.
  - `<why>`에는 이 커밋의 이유만 적고, 다른 커밋의 이유를 섞지 않습니다.
