# 설계 문서 규칙

ADR, README, `docs/local-development.md` 같은 설계 문서를 쓰거나 고칠 때 읽습니다. 형식과 상태 정의는 `docs/adr/README.md`가 기준입니다.

## ADR을 쓰는 때

ADR은 아래 셋 중 하나에 해당할 때만 씁니다. 해당하는 기준을 "맥락"의 첫 줄에 적습니다.

1. **되돌리기 어려운 선택**: 언어, DB, 메시징, 서비스 경계, 외부 노출 여부처럼 바꾸려면 여러 서비스를 다시 짜야 하는 것
2. **여러 서비스가 함께 지켜야 하는 규칙**: 한 곳이라도 어기면 오류 없이 깨지는 것 (예: 같은 토픽의 파티션 수)
3. **대안이 실제로 둘 이상 있었던 결정**: 고른 이유가 코드만 봐서는 드러나지 않는 것

## ADR을 쓰지 않는 것

- 기능 구현 설명(이벤트 필드, 설정값, 재시도 횟수, 테이블 구조): 원본은 코드와 스키마이고, 쓰는 방법은 `docs/local-development.md`에 둡니다.
- 기존 결정의 일부 변경: 새 ADR을 만들지 않고, 기존 ADR의 해당 문장 아래에 `날짜 변경: 무엇이 어떻게` 한 줄을 덧붙입니다. 결정 전체가 뒤집힐 때만 상태를 `대체됨(Superseded by ADR-0xx)`으로 바꾸고 새 ADR을 씁니다.
- 작업 범위, 진행 상황, 할 일

## ADR을 쓰는 방법

- 번호는 마지막 번호의 다음 값을 쓰고, 파일명은 `NNN-주제.md`입니다.
- 구성은 상태, 기록일, 맥락(해당 기준), 고려한 대안, 결정, 이유, 감수하는 점입니다. 숫자, 필드, 명령은 옮겨 적지 않고 원본 위치를 가리킵니다.
- 30줄 안팎을 목표로 합니다.

## 상태

- **확정**: 합의했고, 구현이 있으면 테스트로 검증된 것. 구현·검증된 경우에만 `(구현·검증됨)`을 붙입니다.
- **초안**: 방향은 정했으나 세부를 구현하며 더 검토할 것.
- 코드에 없는 기능을 "구현됨"으로 쓰지 않습니다.

## 함께 맞출 곳

- ADR을 추가하거나 상태를 바꾸면 `docs/adr/README.md`의 표(번호, 주제, 상태)를 같이 고칩니다.
- 실행 명령, 설정 키, 테스트 명령이 바뀌면 `docs/local-development.md`를 같이 고칩니다. 테스트 개수 표도 포함입니다.
- 아키텍처, 기술 스택, 서비스 구성이 바뀌면 README의 흐름도, 기술 스택, 로드맵 체크박스를 같이 고칩니다.
- 문서를 옮기거나 지우면 링크가 끊기지 않는지 확인합니다.

## 쓰지 않는 것

- 이메일 주소, 보유 종목·수량·금액, 계좌, 계정 식별자, 키·토큰은 쓰지 않습니다. 유형으로만 설명합니다.
- 외부 사실은 근거를 남기고, 확인하지 못한 것은 "미확인"으로 표시합니다.
