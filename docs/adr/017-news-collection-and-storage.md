# ADR-017: 뉴스 수집·발행·저장 (news.collected 이벤트, 수집 스케줄, news 서비스)

- 상태: **초안**
- 기록일: 2026-10-23

## 맥락
수집기가 검색 API로 모은 기사를 걸러 낸 뒤, 별도 서비스가 받아 저장해야 한다. 이 기사를 나중에 가격 변동의 원인 근거로 쓰려면 저장소가 필요하다. 서비스끼리는 Kafka 이벤트로만 통신하므로(ADR-006, ADR-010) 기사 한 건을 알리는 이벤트와 수집 주기를 정해야 한다. 같은 기사가 여러 검색어나 종목에 걸려 반복해서 들어오고, Kafka는 같은 메시지를 다시 전달할 수 있다.

## 고려한 대안
- 브리핑이 변동 시점에 검색 API를 직접 조회하고 저장하지 않기: 저장소는 필요 없지만 변동 당시의 기사를 나중에 다시 확인할 수 없고, 호출 횟수가 변동 건수에 비례한다.
- 수집기가 직접 저장하기: 서비스가 DB를 공유하지 않는 원칙(ADR-004, ADR-006)에 어긋난다.
- 기존 `TickListener`에서 `jobType`으로 분기: 시세 수집과 뉴스 수집이 한 클래스에 섞이고, 한쪽의 실패가 다른 쪽에 영향을 준다.
- 한 이벤트에 여러 기사를 담기: 메시지 키(기사 url)와 재처리 단위가 기사 한 건이어야 소비 쪽의 `eventId` 멱등 처리가 단순하다.
- 본문 포함: 검색 API가 제목과 요약만 주고, 저작물과 개인 정보를 이벤트에 싣지 않기 위해 제외한다.

## 결정

### 이벤트 (수집기 → news 서비스)
- 토픽 `news.collected`, 파티션 3개. 발행 쪽과 소비 쪽이 같은 값으로 선언한다(ADR-013). 3은 부하를 재서 정한 값이 아니라 `market.snapshot`과 맞춘 시작값이며, 파티션은 늘릴 수만 있고 늘리면 같은 키가 가는 파티션이 바뀌므로 처음에 여유를 둔다.
- 메시지 키는 기사 `url` 문자열이다. 같은 기사는 항상 같은 파티션으로 가서 순서가 보존된다.
- 봉투는 ADR-010 그대로이다. `occurredAt`은 기사 발행 시각(`publishedAt`), `correlationId`는 수집을 시작시킨 tick의 값을 이어받는다.
- payload: `title`(평문, 1~500자), `summary`(평문, 빈 문자열 허용, 최대 2000자), `url`(uri), `publisher`(출처 도메인), `publishedAt`(date-time), `symbols`(1개 이상, 중복 불가, 6자리 종목코드 또는 시장 전체를 뜻하는 `*`), `matchedQueries`(선택, 중복 불가).
- 본문과 개인 정보(보유 수량, 금액)는 담지 않는다. 스키마는 `additionalProperties`를 막지 않아 소비자가 모르는 필드를 무시한다(ADR-010).
- 길이 초과는 발행 전에 코드 포인트 단위로 잘라 서로게이트 쌍이 끊기지 않게 한다. 종목코드나 url이 스키마를 어기는 기사는 발행하지 않고 건수만 경고한다. 한 번의 수집에서 전부 건너뛰면 설정 실수로 보고 별도 경고를 남긴다.

### 스케줄 (수집기)
- 뉴스 수집용 tick은 `jobType` `collect-news`이고 기본 주기는 15분(`collector.schedule.news-interval-ms`, 기본 900000)이다.
- 타이머는 `collector.schedule.enabled`(환경변수 `COLLECTOR_SCHEDULE_ENABLED`)로 켜고 끈다. 기본값은 꺼짐이며, 기존 시세 수집 tick 타이머에도 적용한다. 로컬에서는 필요할 때만 `scripts/publish-tick.sh <jobType>`로 tick 한 건을 수동 발행한다.
- 뉴스 수집 리스너는 `schedule.tick`을 별도 consumer group(`collector-news`)으로 구독한다. `schedule.tick`은 파티션이 1개라서 기존 리스너와 같은 그룹이면 한쪽만 메시지를 받아 오류 없이 tick이 누락된다. 그룹을 나누면 각 리스너가 모든 tick을 받고 자기 `jobType`만 처리한다.
- `collect-news` tick을 받으면 `NewsCollector.collect()`를 호출하고, 반환된 기사마다 이벤트 한 건을 발행한다. 수집이 예외를 던져도 리스너는 죽지 않고 예외 종류만 경고로 남긴다(검색어와 외부 오류 원문은 로그에 출력하지 않는다).

### 재발행 억제 (수집기)
- 이미 발행한 기사를 메모리 집합에 기록해 다시 발행하지 않는다(상한을 넘으면 비운다). 기록하는 키는 url, 정렬한 `symbols`, 정렬한 `matchedQueries`의 조합이다. 순서만 다른 같은 조합은 다시 발행하지 않는다.
- 같은 url이 새 종목이나 새 검색어로 다시 걸리면 다시 발행한다. 소비 쪽이 종목·검색어를 합집합으로 합치므로, url만 키로 쓰면 새 연결을 받을 기회가 영구히 사라진다.
- 키는 전송 future가 성공으로 끝난 뒤에만 기록한다. 실패한 기사는 기록하지 않아 다음 tick에서 다시 발행된다.

### 저장 (news 서비스)
`news.collected`를 소비해 PostgreSQL에 저장하는 **news 서비스**(Java)를 둔다.
- 스키마 `news`, 서비스 전용 계정. 자기 스키마만 쓴다(ADR-004). 테이블은 `news_article`(기사 한 건), `news_article_symbol`(기사와 종목의 N:M).
- 기사 중복은 `article_key`로 판단한다. 이 서비스가 `url`에서 직접 계산한다: URL 정규화(호스트 소문자, 앞의 `www.` 제거, 스킴 무시, `#조각` 제거, `utm_`로 시작하는 쿼리 제거, 끝의 `/` 제거, 남은 쿼리는 이름·값 순 정렬) 후 SHA-256 소문자 hex. 이벤트에 키가 들어 있어도 쓰지 않는다. 서비스마다 키를 독립적으로 계산하는 것이 설계이며 수집기의 정규화 방식과 달라도 된다.
- 한 트랜잭션에서 순서대로 처리한다: (1) 기사 삽입, 어떤 유니크 제약 충돌이든 `ON CONFLICT DO NOTHING`, (2) 삽입되지 않았으면 `article_key`로 기존 id 조회, (3) 종목 삽입(이미 있으면 무시), (4) 기존 기사면 `matched_queries`를 합집합으로 갱신.
- 본문은 저장하지 않는다. 제목, 요약, URL, 출처, 발행 시각, 종목, 검색어만 둔다. 이벤트는 `eventId`로 멱등하게 처리한다(ADR-010).

### 오류 처리 (news 서비스)
처리에 실패한 메시지(예: 값이 컬럼 길이를 넘어 DB가 거부)는 간격 없이 9번 다시 시도한다(최초 포함 총 10번). 그래도 실패하면 건너뛰되, 건너뛰기 전에 DB 테이블 `failed_event`에 남긴다.
- 남기는 값: 토픽, 파티션, 오프셋, 키, 메시지 원문, 가장 안쪽 원인 예외의 클래스와 메시지(1000자까지), 시도 횟수, 시각. 같은 위치(토픽, 파티션, 오프셋)는 한 행만 남긴다.
- 별도 DLT 토픽은 두지 않는다. 사람이 SQL로 바로 보고 원인을 확인하는 것이 목적이고, DLT를 다시 읽어 처리하는 소비자는 이번 범위에 없다.
- 기록 자체가 실패하면(예: DB 중단) 예외를 던져서 레코드를 건너뛰지 않고 다시 시도한다. 보관하지 못한 채 유실되는 것을 막기 위함이다.
- 재시도 횟수는 Spring Kafka 기본 오류 처리기와 같은 값을 명시적으로 유지한다.

## 이유
1. 기사 한 건이 이벤트 한 건이면 재시도와 멱등 처리 단위가 같다. url을 키로 쓰면 같은 기사의 이벤트가 한 파티션에 모인다.
2. `event_id` 유니크만으로는 같은 이벤트의 재전달만 막고, 같은 기사가 다른 이벤트로 다시 오는 경우는 막지 못한다. `article_key` 유니크로 둘 다 막는다.
3. 같은 기사가 다른 종목·검색어로 다시 오면 새 행 대신 기존 행에 종목과 검색어를 합쳐서, 종목별 조회가 중복 없이 한 기사를 돌려준다.
4. 스케줄을 기본 꺼짐으로 두면 로컬에서 의도하지 않은 외부 호출이 일어나지 않는다.

## 감수하는 점
- 재발행 억제는 메모리 기반이라 재시작하면 초기화된다. url 문자열이 그대로 같을 때만 막으므로 `www.`이나 `utm_` 파라미터만 다른 url은 다시 발행될 수 있다. 같은 기사가 새 종목·검색어로 걸려 다시 발행되는 것은 의도한 동작이며, 중복은 news 서비스의 DB가 최종으로 막는다.
- URL이 다르면 같은 내용도 다른 기사로 저장된다(제목 유사도 기반 중복 제거는 하지 않는다). 경로의 대소문자는 구분한다. 서버에 따라 같은 문서일 수 있지만 구분하지 않으면 다른 문서를 합칠 위험이 있다.
- 스케줄 기본 꺼짐으로 기존 시세 수집 tick도 기본으로 멈춘다. 켜려면 `COLLECTOR_SCHEDULE_ENABLED=true`이거나 수동 발행이 필요하다.
- 수동 발행 스크립트는 컨테이너 안의 콘솔 프로듀서가 `localhost:9092`로 접속하는 구성에서 확인했다. 브로커 광고 주소가 다르면 컨테이너 이름이나 주소를 바꿔야 한다.
- `failed_event`의 원문과 예외 메시지에는 기사 내용이 들어갈 수 있다. 이 서비스의 스키마 안에만 두며, 자동 삭제는 하지 않는다. 쌓인 레코드를 다시 처리하는 기능은 없고, 시도 횟수는 실제 값이 아니라 설정에서 계산한 총 시도 횟수(10)를 저장한다. 재시도 대상이 아닌 예외(예: 형변환 오류)는 재시도 없이 바로 보관되지만 이때도 10으로 저장된다.
- 복구기가 계속 실패하면(DB 중단 등) 같은 레코드를 간격 없이 반복해서 다시 시도하므로, 그 파티션의 처리는 DB가 돌아올 때까지 멈추고 로그가 빠르게 늘어난다.

## 보관 기간
보관 기간은 90일로 정한다. 삭제 작업은 이번 범위에 없고 구현되지 않았다. 후속에서 `published_at` 인덱스를 이용한 정리 작업으로 구현한다.

## 검증
- 계약: `NewsCollectedContractTest`(수집기)가 샘플 통과, 잘못된 종목코드·빈/중복 `symbols`·형식 오류·필수 필드 누락 거부, 모르는 필드 무시를 확인한다. `NewsContractTest`(news 서비스)는 샘플의 스키마 통과, 소비자 파싱, 모르는 필드 무시, 소비자가 읽는 필드가 스키마의 필수 항목에 있는지를 확인한다.
- 발행: `NewsPublisherTest`, `NewsTickListenerTest`, `TickPublisherTest`가 tick에서 이벤트 N건(키=url, 스키마 통과), 재발행 억제, 전송 실패 시 재시도, 수집 예외에도 리스너 생존, consumer group 분리, 타이머 기본 꺼짐을 확인한다. `TopicsConfigTest`는 양쪽 서비스의 토픽 이름과 파티션 수를 확인한다.
- 저장: 격리한 실제 Postgres·Kafka에서 같은 `eventId` 재전송, URL 변형(`www.`, `utm_`)이 다른 같은 기사, 종목과 검색어 합집합, 종목 삽입 실패 시 기사 행 롤백을 확인했다. 종목코드가 컬럼 길이를 넘는 메시지는 9번 재시도 후 원문 그대로 `failed_event`에 한 행이 남고 기사 행은 생기지 않으며, 뒤의 정상 메시지는 이어서 저장된다. `failed_event`를 일부러 막으면 레코드를 건너뛰지 않고 재시도하다가, 복구하면 저장하고 진행한다.
- 흐름: 실제 검색 API 호출 1회로 수집 → 필터 → 발행 → 저장을 확인했고, 같은 tick을 다시 보내도 재발행과 중복 저장이 없었다.
- 기존 DB 볼륨에 `02-roles-news.sql`을 수동 적용하는 경로는 확인하지 않았다.

## 구현 메모
서비스 전용 계정·스키마는 `infra/compose/postgres/init/02-roles-news.sql`이 만든다. 초기화 스크립트는 DB 볼륨을 처음 만들 때만 실행되므로, 이미 볼륨이 있으면 이 스크립트를 DB에 직접 적용해야 한다(볼륨을 지우면 기존 데이터가 사라진다).

## 후속
- 90일 보관 정리 작업(`failed_event`의 보관 기간도 함께 정한다).
- `failed_event` 재처리가 필요해지면 DLT 토픽 도입을 다시 검토한다.
- 복구기가 실패하는 동안 재시도 간격이 0이라 로그가 빠르게 늘어난다. 운영에서 DB 중단이 길어질 수 있으면 간격을 두는 것을 검토한다.
- 재시작에도 유지되는 재발행 억제(ADR-012의 DB 기반 중복 방지와 함께 검토).
