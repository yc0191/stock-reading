# ADR-014: 이슈 조치 판정은 운영 서버의 확인기가 저장소 기준 파일로 재고, GitHub Actions가 결과를 이슈에 전달한다

- 상태: **초안** (구현됨, 운영 첫 장날 확인 전)
- 기록일: 2026-11-18

## 맥락
기준 3(대안이 둘 이상)·기준 2(여러 곳이 함께 지키는 규칙)
운영 문제를 고친 뒤에는 정해 둔 측정일(장날 2일)에 운영 DB를 조회해 효과를 판정한다. 이 조회를 사람이 세션을 켜 두고 그 시각에 서버에 들어가 하면, 세션이 꺼진 날은 측정일을 놓치고 지난 날의 자료로는 다시 잴 수 없다. 사람 없이 측정일마다 재고 결과를 남기는 방법이 필요하다.
확인기와 판정 워크플로는 기준 파일 형식, 결과 파일 칸, 공개 범위를 함께 지켜야 한다. 한쪽만 바꾸면 결과가 오류 없이 무효가 된다.

## 고려한 대안
1. 세션 안 예약과 브라우저 SSH: 세션이 꺼지면 측정일을 놓치고, 서버 접속은 사람이 직접 해야 한다(ADR-007).
2. 노트북 예약 실행: 노트북이 꺼지거나 오프라인이면 놓치고, 운영 DB에 닿는 길을 따로 열어야 한다.
3. 서버 타이머로 도는 짧은 작업: 시각이 고정이라 휴장일 판단을 따로 해야 한다. 휴장 판단은 수집기에만 둔다.
4. Redis·DB 안에서 쿼리를 관리: 기준이 코드 리뷰와 배포 이력 밖에 있어, 어느 기준으로 쟀는지 대조할 수 없다.
5. LLM 판별: 토큰 비용이 들고, 같은 입력에 같은 판정이 보장되지 않는다.

## 결정
- 서비스 서버에 확인기(`services/ops-checker`)를 상주시킨다. 수집기의 판 시작 알림(`daily.collection.completed`)을 받아 실행하고, 휴장이면 계산 없이 휴장 결과만 남긴다. 같은 알림은 `eventId`로 한 번만 처리한다.
- 판정 기준은 저장소의 기준 파일(`ops-checks/`)이다. 이미지에 실려 배포되고, 결과마다 파일 바이트의 SHA-256 지문을 남겨 어느 기준으로 쟀는지 대조한다. 형식의 원본은 `services/ops-checker/src/ops_checker/criteria.py`다.
- 지표 SQL은 읽기 전용 계정으로 계산한다. 이 계정은 market·briefing 스키마를 앞으로 생길 표까지 읽고, personal에는 권한이 없으며, 쓰기는 `ops` 스키마(`infra/db/ops/`)에만 한다. 필요한 표·열만 읽는다는 ADR-004의 읽기 규칙에 대한 예외이며, 이유는 지표마다 읽는 표가 달라 기준 파일을 쓸 때마다 권한을 고치지 않기 위해서다.
- 결과는 DB `ops` 장부와 S3 결과 파일에 남긴다. 파일에는 비율·판정·버전·지문만 담는다(`results.py`). 확인기는 결과 파일을 올리기만 하는 전용 사용자의 키로 올리고, 서버 계정의 키는 받지 않는다.
- 판정은 GitHub Actions(`.github/workflows/ops-verdict.yml`, `scripts/ops_verdict.py`)가 한다. 서버가 밖으로 나가 결과를 올리고(ADR-007), Actions가 결과 버킷을 읽어 지문과 조치 커밋의 운영 반영을 확인하고 측정일을 세어 `verifying` 이슈에 댓글을 달고, 측정일이 차면 통과·실패를 최종 댓글로 남기고 `verifying`을 뗀다. 이슈를 닫는 것은 사람이다.
- 확인기는 결과 파일을 올린 직후 이 저장소의 Actions 실행만 되는 토큰으로 판정 워크플로를 부른다. 평일 예약 실행은 그 요청이 실패한 날의 대비로 남긴다.
- 결과 파일이 없거나 오류가 있으면 작업을 실패로 끝내 GitHub 실패 알림으로 확인기·수집기의 멈춤을 알린다.
- 판정은 SQL 지표로만 한다. LLM으로 판별하지 않고, 사람이 확인할 항목도 두지 않는다. SQL로 잴 수 없는 것은 지표로 삼지 않는다.
- 공개 저장소이므로 댓글과 로그에는 비율·판정·날짜·버전·이슈 번호·실패 종류만 쓴다. 건수·종목·서버 주소·버킷 이름·SQL 본문은 쓰지 않는다.

원본: 기준 파일 형식과 계산은 `services/ops-checker/`, 결과 버킷과 권한은 `infra/terraform/ops_results.tf`, 쓰는 법과 운영 반영은 `docs/dev/services.md`·`infra/deploy/README.md`, 판정 절차는 `docs/incidents/README.md`다.

## 이유
1. 서버에서 알림으로 도는 확인기는 세션·노트북과 무관하고, 휴장일에는 계산하지 않아 측정일에 세지 않는다.
2. 기준을 저장소 파일로 두면 기준 변경이 코드 리뷰를 거치고, 지문으로 결과와 기준을 대조해 기준을 바꾼 결과를 걸러 낼 수 있다.
3. 서버는 결과를 올리기만 하고 Actions가 읽기만 하므로 서버에 들어오는 길을 열지 않는다.
4. 계산은 코드가 하므로 같은 자료는 같은 판정이다.

## 감수하는 점
- 결과 파일 올리기에 실패한 날의 결과는 다시 만들 수 없다. 수동 재계산 명령은 아직 없다.
- 확인기가 읽는 표가 바뀌면 기준 파일의 SQL이 깨질 수 있다. 해당 지표는 `error`로 기록되어 실패 알림으로 보인다.
- 서버에 GitHub 토큰을 둔다. 이 저장소의 Actions 실행만 되며, 만료되거나 요청이 실패한 날은 늦게 도는 예약 실행이 판정한다.
