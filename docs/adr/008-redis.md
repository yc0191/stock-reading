# ADR-008: 캐시와 카운터 저장소로 Redis를 사용한다

- 상태: **확정** (아직 미구현 — 해당 기능이 들어올 때 도입)
- 기록일: 2026-10-20

## 맥락
외부 API(뉴스, 시세, LLM)에는 호출 한도가 있고 LLM 호출은 느리고 비용이 든다. 이를 서비스 인스턴스 사이에서 공유해 제어할 저장소가 필요하다.

## 고려한 대안
Valkey(BSD 포크), Memcached, Redis 없이 PostgreSQL만 사용

## 결정
Redis를 사용한다. 용도는 다음과 같다.
1. 외부 API 호출 예산 관리(일일 한도 카운터, 속도 제한)
2. LLM 결과 캐시(요인 × 시간창 × 프롬프트 버전 키)

## 이유
1. 두 용도는 ADR-005의 부하 지점(외부 API 한도 제어, 급변동 시 LLM 호출 폭주)과 직접 이어진다.
2. 공유 카운터와 TTL 캐시는 Redis의 기본 용도에 가장 잘 맞는다.
3. Kafka와 함께 쓰는 백엔드 구성의 경험이라는 프로젝트 목표와 일치한다.

## Redis를 쓰지 않는 용도와 이유
- 현재가 캐시, 등락률 랭킹: 조회 트래픽이 없음
- 뉴스 중복 제거, 이벤트 멱등 처리, 알림 중복 방지: DB 유니크 제약과 트랜잭션이 더 정확함(Redis와 DB는 한 트랜잭션으로 묶이지 않음)
- 스케줄 분산락: 수집기 인스턴스가 1개인 동안은 불필요

## 호출 한도 카운터를 위한 준비
- 시세 호출 상한은 `CallRateLimit` 인터페이스(collector `marketdata`) 뒤에 있다. 지금은 인스턴스 메모리 구현만 있고, Redis 구현은 같은 인터페이스를 구현해 빈만 바꿔 끼운다.
- 제공자 한도는 앱 전체(초당 40회)와 API별(초당 20회) 두 단위다. 시세 외 조회(일봉, 지수 등)가 들어오면 앱 전체 한도를 서비스 사이에서 나눠 써야 하므로 카운터 키는 앱 단위와 API 단위를 모두 갖게 한다.
- 실제 서버는 공식 API별 한도보다 낮은 초당 13회에서 한도 초과가 났다([S04](../test-history/S04-quote-real-api/results.md)). 카운터의 상한값은 공식 수치가 아니라 관측한 지속 속도(초당 12회 이하)를 기준으로 정한다.

## 설계 시 고려할 점
카운터 영속성, 메모리 부족 시 키 제거 정책, LLM 캐시 키에 프롬프트 버전 포함(RAG 실험 결과가 섞이지 않게).
