# ADR-006: 서비스를 분리한 MSA로 구현하되, 분리 기준과 한계를 명시한다

- 상태: **확정**
- 기록일: 2026-10-20

## 맥락
기준 1(되돌리기 어려운 선택): 서비스 경계는 나중에 바꾸기 어렵다. 트래픽이 작아 MSA가 과할 수 있다는 점을 알고 정한다.

## 고려한 대안
단일 모놀리스, 모듈러 모놀리스, MSA

## 결정
서비스 단위로 분리한 MSA로 구현한다.

| 서비스 | 역할 | 언어 |
|---|---|---|
| collector (수집기) | 외부 데이터 수집, 타이머 | Java |
| market (시세처리기) | 시세 저장, 변동 감지, ETF 구성 종목 | Java |
| news (뉴스처리기) | 기사 저장과 조회 | Java |
| briefing (브리핑 AI) | 근거 선택·설명 생성 | Python |
| notifier (발송기) | 이메일 발송 | Java |

개인 데이터(멤버, 메일 주소·수신 설정, 포트폴리오)는 personal 스키마의 표에 둔다. 메일 주소는 발송기만 읽고, 이벤트에는 멤버 번호만 싣는다. 알림 판단을 맡는 개인화 서비스를 만들면 이 표를 넘겨받는다.

## 분리 기준
변경 이유 / 실패 특성 / 확장 특성 / 언어·런타임 중 하나 이상이 다르면 나눈다. 같은 외부 접점과 같은 스케줄을 공유하는 수집 기능은 하나로 합친다.

## 이유
1. **장애 격리:** 발송이 실패해도 시세 처리와 브리핑 생성은 계속되고, 발송기가 복구되면 밀린 이벤트를 이어서 처리한다.
2. **독립 확장:** 병목이 되는 브리핑(LLM 호출)만 인스턴스를 늘릴 수 있다.
3. **기술 이질성:** Python 브리핑과 Java 서비스의 경계가 자연스럽다.
4. **데이터 소유 분리:** 서비스별 스키마와 계정(ADR-004).

## 서비스 간 규칙
- 서비스 사이에 일어난 일(알림)은 Kafka 이벤트로 주고받는다. 다른 서비스의 스키마에는 쓰지 않는다.
  - 2026-11-13 변경: 이미 저장된 자료를 묻는 조회는 Kafka 요청·응답 대신 자료를 가진 서비스의 내부 조회 API를 HTTP로 직접 부른다(조회는 내부 HTTP, 알림은 Kafka). 브리핑이 시세처리기·뉴스처리기에 근거를 물으며 응답 토픽에서 기다리면 요청·처리·응답 중 어디서 멈췄는지 알 수 없었고, 기사가 다 저장됐는지도 추측해야 했다. 조회 API는 서버 밖으로 열지 않고(ADR-007), 다시 부르는 규칙의 원본은 브리핑 `config.py`의 `QuerySettings`, 경로는 `docs/local-development.md`의 "내부 조회 API"다. 기사 저장이 끝났다는 사실은 뉴스처리기의 알림(`news.stored`)으로 받는다.
- 개인 정보는 일반 이벤트에 넣지 않는다.

## 감수하는 점
- 물리적 분산이 아니라 논리적 분리다.
- 분산 환경의 비용(네트워크 지연, 디버깅, 이벤트 중복)을 진다. `eventId` 멱등 처리와 스키마 버전 관리로 줄인다.
- 조회 대상 서비스가 멈춰 있으면 조회가 다시 부르기 끝에 실패한다. 급변동은 그 작업이 실패해 메일이 나가지 않고, 데일리 판은 그 자료가 빠진 채 나간다(둘 다 Kafka 요청·응답 때와 같다). Kafka처럼 대신 쌓아 두었다가 나중에 답하지 않는다. 메일 하나의 추적 ID로 호출 기록(`briefing.job_step`)과 다섯 서비스의 로그를 함께 찾아 원인을 본다.
