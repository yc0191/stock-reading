# ADR-006: 서비스를 분리한 MSA로 구현하되, 분리 기준과 한계를 명시한다

- 상태: **확정** (민감 데이터 경로 예외는 구현 단계로 이월)
- 기록일: 2026-10-20

## 맥락
실서비스 트래픽이 작다. 이 조건에서 MSA는 오버엔지니어링일 수 있음을 인지한다.

## 고려한 대안
단일 모놀리스, 모듈러 모놀리스, MSA

## 결정
서비스 단위로 분리한 MSA로 구현한다.

## 서비스 구성
| 서비스 | 역할 | 언어 |
|---|---|---|
| collector (수집기) | 외부 데이터 수집, 타이머 | Java |
| market (시세처리기) | 시세 저장, 변동 감지 | Java |
| news (뉴스처리기) | 기사 저장과 조회 | Java |
| briefing (브리핑 AI) | 근거 선택·설명 생성 | Python |
| personal (개인화 서비스) | 알림 판단 + 개인 데이터 보유 (미착수) | Java |
| notifier (발송기) | 이메일 발송 | Java |

2026-11-10 변경: ETF 구성 종목은 시세처리기가 운용사 사이트에서 직접 받는다. 변경 감지와 지수 교체 일정이 시세처리기 DB에 있어 한 서비스에서 끝내려는 것이며 자세한 것은 docs/local-development.md.

개인화 서비스는 알림 판단과 개인 데이터 보유를 한 서비스에 두고 시작한다(서비스 수 절감, 민감 데이터 경계 유지). 메모리 실측 후 필요하면 분리한다.

2026-11-11 변경: 개인 데이터(멤버, 메일 주소·수신 설정, 포트폴리오)는 개인화 서비스를 만들기 전에 personal 스키마의 표로 먼저 둔다. 값은 사람이 SQL로 넣고, 메일 주소는 발송기만 읽으며, 데일리 판 이벤트에는 멤버 번호만 싣는다. 개인화 서비스를 만들면 이 표를 넘겨받는다.

## 이유
1. **장애 격리:** 발송이 실패해도 시세 처리와 브리핑 생성은 계속된다. 발송기를 중단했다가 복구해 이벤트가 이어서 처리되는 모습을 시연할 수 있다.
2. **독립 확장:** 병목이 되는 브리핑 AI(LLM 호출, 임베딩)만 인스턴스를 늘릴 수 있다.
3. **기술 이질성:** Python 브리핑 AI와 Java 서비스의 경계가 자연스럽다.
4. **데이터 소유 분리:** 서비스별 DB 스키마와 계정(ADR-004).
5. **학습 목표:** 각 컨테이너(서비스) 사이의 **병목과 네트워킹을 실제로 제어**해 보는 경험.

## 서비스 분리 기준
아래 중 하나 이상이 다르면 서비스를 분리한다: 변경 이유 / 실패 특성 / 확장 특성 / 언어·런타임.
같은 외부 접점과 같은 스케줄을 공유하는 수집 기능은 하나로 합친다.

## 서비스 간 규칙
- 서비스 간 통신은 Kafka 이벤트로 한다.
- 다른 서비스의 DB 스키마를 직접 쓰지 않는다.
- 조회 요청은 LLM 에이전트(MCP)를 외부 입구로 두는 방향이며 지금은 외부 접속을 열지 않는다(ADR-007).
- 민감 데이터(개인 정보)는 일반 이벤트에 넣지 않는다. 이를 담은 메시지의 전달 경로는 구현 단계에서 정한다.

## 감수하는 점
- 개발 인원이 적어 팀별 독립 개발이라는 조직적 이점은 없다.
- 서버 2대라 물리적 분산이 아닌 논리적 분리다.
- 분산 환경의 비용(네트워크 지연, 디버깅, 이벤트 중복 처리)을 감수하며, 이를 직접 겪고 해결하는 것이 학습 목표다.
- 완화: 멱등 처리(`eventId`), 중복 방지, 이벤트 스키마 버전 관리, 모니터링(후순위).
