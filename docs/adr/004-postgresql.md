# ADR-004: PostgreSQL + pgvector, 서비스별 스키마와 계정

- 상태: **확정**
- 기록일: 2026-10-20

## 맥락
기준 1(되돌리기 어려운 선택): 시세·뉴스·멤버 같은 관계형 데이터와 근거 검색용 벡터 검색이 모두 필요하고, 컨테이너 수는 적게 유지하고 싶다.

## 고려한 대안
MySQL, MongoDB, OpenSearch/Elasticsearch, TimescaleDB, DynamoDB/Cassandra

## 결정
**PostgreSQL + pgvector**. 한 인스턴스 안에서 서비스별로 **스키마와 DB 계정**을 나누고, 서비스는 자기 스키마에만 쓴다.

2026-11-11 변경: 종목·검색어·멤버 같은 업무 데이터는 DB 표가 원본이고, 다른 서비스는 필요한 표·열만 읽기 전용 권한으로 직접 읽는다. 같은 목록을 이벤트로 퍼뜨리면 서비스마다 어긋나 종목이 오류 없이 빠질 수 있어서다. 계정별 권한의 원본은 `infra/db/personal/init.sql`과 마이그레이션이다.

## 이유 (문서로 확인)
1. **벡터 검색을 같은 DB에서:** pgvector가 HNSW·IVFFlat 인덱스와 거리 계산을 지원해 별도 벡터 DB가 필요 없다.
2. **MySQL은 이 용도에 맞지 않았다:** 벡터 거리 함수가 일부 에디션 전용이고 벡터 컬럼에 인덱스를 걸 수 없었다(검토 당시 기준).
3. **서비스별 분리가 자연스럽다:** PostgreSQL의 스키마는 DB 안의 이름 공간이라 한 인스턴스에서 서비스별로 나눌 수 있다.

## 비교 요약
- MongoDB: 벡터 검색이 별도 프로세스가 필요하고 성숙도가 미확인이라 대안으로 남김.
- OpenSearch: 키워드+벡터 하이브리드에 강하나 메인 DB로는 맞지 않음. 근거 검색 개선 단계의 비교 대상.
- TimescaleDB, DynamoDB/Cassandra: 데이터 규모에 비해 과함.

## 감수하는 점
- 벡터 인덱스(HNSW)는 메모리를 더 쓴다. 실측 후 IVFFlat을 검토한다.
- 벡터 규모가 커지면 한계가 있어, 벡터 저장소는 교체할 수 있게 인터페이스 뒤에 둔다.
