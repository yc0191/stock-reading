# ADR-018: 장 마감 후 조회 정보 이벤트 (market.insight)

- 상태: **초안**
- 기록일: 2026-10-27

## 맥락
가격 변동의 이유를 설명하려면 장 마감 후의 일봉, 세계지수, 환율종합, 시장종합 정보가 필요하다. 수집기가 이 4가지 API를 조회하고, market 서비스가 받아 저장한다. 서비스끼리는 Kafka 이벤트로만 통신하므로(ADR-006, ADR-010) 이 응답을 나르는 이벤트와 토픽을 정해야 한다. 조회 응답은 trim 외에 가공하지 않고 원문 그대로 보관하는 것이 프로젝트 규칙이며, 응답 내부 필드는 이번 범위에서 해석하지 않는다.

## 고려한 대안
- API별로 이벤트와 토픽을 4개 두기: 응답 모양이 API마다 달라 계약이 명확해 보이지만, 이번 범위는 응답 내부를 해석하지 않으므로 4개의 스키마가 모두 "봉투 + 불투명 응답"으로 같다. 토픽 선언이 서비스마다 4곳으로 늘고, 파티션 수가 어긋나면 오류 없이 누락되는 위험(ADR-013)이 4배가 된다. API를 추가할 때마다 토픽과 선언을 늘려야 한다.
- 한 이벤트에 4개 응답을 모두 담기: 한 API가 실패하면 나머지까지 발행하지 못하거나 부분 이벤트가 생긴다. 재처리 단위도 커진다.
- 응답을 객체(JSON 노드)로 싣기: 직렬화 과정에서 숫자 표기나 공백이 바뀔 수 있어 원문 보존 원칙을 지키기 어렵다.

## 결정

### 이벤트 (수집기 → market 서비스)
- 응답 한 건이 이벤트 한 건이다. API 4종을 `market.insight` 이벤트 하나로 묶고 `payload.apiType`으로 구분한다.
- eventType `market.insight`, 토픽 `market.insight`, 파티션 3개. 발행 쪽(collector)과 소비 쪽(market)이 같은 값으로 선언한다(ADR-013). 3은 부하를 재서 정한 값이 아니라 `market.snapshot`, `news.collected`와 맞춘 시작값이다.
- 메시지 키는 `<apiType>:<target>`이고 target이 null이면 `apiType`만 쓴다. 같은 대상의 응답은 같은 파티션으로 간다. 순서에 의존하는 처리는 없다.
- 봉투는 ADR-010 그대로이다. `occurredAt`은 조회 시각(`fetchedAt`), `correlationId`는 조회를 시작시킨 tick의 값을 이어받는다.
- payload:

| 필드 | 내용 |
|---|---|
| `apiType` | `daily-price`(일봉), `world-index`(세계지수), `exchange-rate-summary`(환율종합), `market-summary`(시장종합) |
| `target` | 조회 대상 구분값. 일봉은 종목코드(6자리), 세계지수는 대륙구분, 환율종합·시장종합은 `null`. 필드는 항상 있다 |
| `response` | 응답 본문 원문 문자열. trim 외에 가공하지 않는다. 소비자는 해석하지 않고 그대로 저장한다 |
| `scheduledFor` | 조회를 일으킨 `schedule.tick`의 논리적 시각 |
| `fetchedAt` | 응답을 실제로 받은 시각 |

- `response`를 객체가 아닌 문자열로 두는 이유는 직렬화 때문에 숫자 표기나 공백이 바뀌는 것을 막기 위해서다. market은 이 문자열을 jsonb로 저장한다. jsonb는 키 순서와 공백을 정규화하므로 "원문"은 값 수준의 보존이다.
- `apiType`별 `target` 형식은 스키마의 조건(`if`/`then`)으로 검증한다. 대륙구분은 실제 값 목록을 확인하지 못해 형식(비어 있지 않은 문자열)만 검사한다. 알 수 없는 `apiType`은 스키마를 통과하지 못하므로 새 API를 추가하면 스키마 enum을 함께 늘린다.
- 스키마는 `additionalProperties`를 막지 않아 소비자가 모르는 필드를 무시한다(ADR-010).

### 트리거
- `schedule.tick`의 `jobType` 알려진 값에 `collect-post-close`를 추가한다. 필드 구조는 바꾸지 않는다. 별도 consumer group으로 구독해야 하는 점은 ADR-017의 `collect-news`와 같다(`schedule.tick`은 파티션 1개).
- 이벤트는 `eventId`로 멱등하게 처리한다(ADR-010). 같은 tick(`jobType`, `scheduledFor`)은 한 번만 처리한다.

## 이유
1. 응답 내부를 해석하지 않는 동안 4종의 계약은 같으므로 이벤트와 토픽을 하나로 묶으면 선언 지점과 파티션 불일치 위험이 늘지 않는다.
2. 응답 한 건이 이벤트 한 건이면 한 API나 한 종목의 실패가 다른 응답의 발행에 영향을 주지 않고, 재시도와 멱등 처리 단위가 같다.
3. 응답을 문자열로 두면 원문 보존 원칙을 계약 수준에서 지킬 수 있다.

## 감수하는 점
- 한 토픽에 응답 모양이 다른 메시지가 섞인다. 소비자는 `apiType`으로 분기해야 하고 응답 내부의 계약은 이 이벤트가 보장하지 않는다. 응답 내부를 해석하게 되면 API별 스키마나 별도 이벤트로 나누는 것을 다시 검토한다.
- 응답을 문자열로 싣기 때문에 JSON 이스케이프로 크기가 약간 커진다.
- 휴장일 판정은 이번 범위가 아니므로 휴장일에도 이벤트가 발행될 수 있다.
