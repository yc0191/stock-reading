# ADR-012: 수집기 자신의 수집은 서비스 안 타이머로 돌리고, 수동 실행은 명령 토픽으로 받는다

- 상태: **확정** (구현·운영 확인)
- 기록일: 2026-11-11

## 맥락
기준 1(되돌리기 어려운 선택): 수집을 어떤 신호로 시작하는지는 수집기·브리핑·시세처리기와 운영 스크립트가 함께 기대는 구조다.
수집기는 자기 수집 작업 다섯 개(`CollectorJobs.Job`)를 `schedule.tick`으로 자기에게 보내고 다시 받아 실행했다. 알림이 밀리면 쌓였다가 한꺼번에 와서 호출 상한에 걸렸고, 이를 막는 보완 코드(가장 늦은 tick만 조회, 오래된 tick 버림)와 리스너마다 따로 둔 consumer group이 필요했다. 사람이 로컬에서 수집을 한 번 돌릴 때도 같은 tick을 손으로 보냈다.

## 고려한 대안
1. 지금 구조 유지: tick이 밀리는 문제를 보완 코드로 계속 막는다.
2. 스케줄 전용 서비스: 시각 판단을 한 서비스에 모으고 모든 서비스에 tick을 보낸다. 서비스와 배포 단위가 하나 늘고, 밀림 문제는 그대로 Kafka에 남는다.
3. 서비스 안 타이머와 명령 토픽(채택).

## 결정
- 수집기 자신의 수집은 수집기 안 타이머(`@Scheduled`)가 실행 입구(`CollectorJobs`)를 직접 부른다. 같은 작업은 겹쳐 돌지 않고, 밀린 회차는 몰아서 실행하지 않는다.
- 사람이 작업 하나를 지금 1회 돌리는 입구로 `collector.command` 토픽을 둔다. 수집기만 선언하고 읽는다. 받는 규칙의 원본은 `contracts/events/collector.command.v1.schema.json`, 쓰는 법은 `docs/local-development.md`(수동 실행)다.
- 남는 `schedule.tick`은 다른 서비스로 가는 신호 셋뿐이다: 데일리 판 시작 `daily-briefing-morning`·`daily-briefing-post-close`(브리핑), 구성 종목 조회 `collect-members`(시세처리기).

## 이유
1. 같은 서비스 안의 시각 실행은 타이머로 충분하다. ADR-006의 "서비스 간 통신은 Kafka 이벤트로 한다"는 서비스 사이의 규칙이고, 서비스 안 타이머는 서비스 간 통신이 아니다.
2. 명령 토픽은 HTTP 같은 바깥 접속을 열지 않고(ADR-007) 사람이 수집기를 움직이는 입구다. 서비스 간 규칙도 그대로 지킨다.
3. 밀림 보완 코드와 수집기 리스너 다섯 개가 없어져 tick 누락·중복을 걱정할 곳이 줄었다.

## 감수하는 점
- 수집기 인스턴스를 여러 개 띄우면 타이머가 인스턴스마다 돈다. 지금은 하나이며, 늘릴 때 다시 정한다.
- 명령 결과는 수집기 로그와 평소 발행 이벤트로만 보인다. 건너뛰거나 무시한 명령의 응답 이벤트는 없다.
