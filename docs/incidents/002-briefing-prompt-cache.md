# 002. 브리핑이 같은 지시문을 매번 정가로 보냄

- 상태: 진행 중(시도 1) - 조치는 develop에 들어갈 예정이고, 운영 배포 뒤 장중 2일로 판정합니다
- 기록일: 2026-11-13
- 관련: 이슈 #48

## 증상

브리핑은 Claude를 부를 때마다 응답 스키마와 긴 시스템 지시문을 함께 보냅니다. 급변동 리포트 하나에서도 처음 작성, 검색어 만들기, 근거가 약한 문장 다시 쓰기로 몇 분 안에 여러 번 부르는데, 프롬프트 캐싱을 쓰지 않아 같은 앞부분을 부를 때마다 정가로 냈습니다.

## 조사

- **바뀌는 값이 섞였는지:** 지시문에 시각이나 작업 id는 없습니다. 끼워 넣는 값은 보합 폭과 최대 검색어 수인데 둘 다 설정값이라 실행 중에 바뀌지 않습니다.
- **다시 쓰기의 앞부분:** 다시 쓰기는 원래 지시문 뒤에 덧붙임을 이어 붙인 문자열 하나로 보냈습니다. 캐시는 앞부분이 한 글자라도 다르면 맞지 않으므로, 이 모양으로는 처음 작성의 캐시를 읽을 수 없습니다.
- **응답 스키마의 위치 (실측):** 스키마(`output_config.format`)가 캐시되는 앞부분에 드는지는 공식 문서에서 찾지 못했습니다. 같은 지시문에 스키마만 바꿔 실제로 불러 보니 캐시를 전혀 읽지 못했고, 같은 요청을 다시 보내면 전부 읽었습니다. 스키마는 앞부분에, 그것도 지시문보다 앞에 듭니다.
- **최소 길이:** 기본 모델은 앞부분이 일정 길이보다 짧으면 표시를 붙여도 캐시하지 않습니다. 가장 짧은 검색어 지시문도 이 길이를 넘는 것을 실측으로 확인했습니다.

## 원인

캐싱을 쓰지 않았습니다(확정). 다시 쓰기는 캐싱을 켜더라도 앞부분이 달라 처음 작성의 캐시를 읽을 수 없는 모양이었습니다.

## 고친 것과 고르지 않은 대안

시스템 지시문 블록에 기본 5분 캐싱 표시를 붙이고, 다시 쓰기는 원래 지시문과 덧붙임을 두 블록으로 나눠 첫 블록이 처음 작성과 같게 했습니다. 효과를 재려고 호출마다 사용량(캐시 쓰기·읽기, 일반 입력, 출력)을 작업 기록과 로그에 남깁니다.

| 선택지 | 판단 |
|---|---|
| **모든 호출에 표시 (고름)** | 표시를 붙이는 곳이 Claude 호출 함수 하나라 예외 규칙이 없습니다. 하루 한 번인 데일리 처음 작성은 다시 읽히지 않아 저장 값만 더 내지만 금액이 아주 작습니다 |
| 호출마다 골라 붙이기 | 위 손해는 없지만 실패 뒤 재시도에서 아끼는 것도 없고, 인자와 테스트만 늘어납니다 |
| **5분 유지 (고름)** | 아끼는 곳은 한 작업 안의 호출들이고, 재검색 전체 상한(4분) 때문에 대개 5분 안에 이어집니다 |
| 1시간 | 처음 저장 값이 더 비쌉니다. 서로 다른 급변동 작업이 한 시간 안에 이어질 때만 이득인데 그 빈도를 모릅니다 |
| **데일리 다시 쓰기 스키마는 그대로 (고름)** | 아침 판·마감 후 판 다시 쓰기는 처음 작성과 스키마가 달라 처음 작성의 캐시는 못 읽고, 다시 쓰기끼리만 나눕니다 |
| 다시 쓰기도 판별 스키마로 맞추기 | 처음 작성의 캐시까지 읽지만 응답 모양과 해석 코드가 바뀌어 비용 이슈보다 범위가 큽니다 |

감수하는 점: 캐시되는 것은 코드에 상수로 있는 스키마와 지시문뿐입니다. 작업마다 다른 근거 자료는 캐시되지 않고 입력의 대부분을 차지하므로, 전체 입력 비용의 절감 폭은 지시문 부분의 절감 폭보다 훨씬 작습니다.

## 시도와 결과

### 시도 1: 지시문 블록 캐싱과 사용량 기록

- 가설: 한 작업 안에서 이어지는 호출이 같은 앞부분을 캐시에서 읽어 입력 비용이 준다.
- 배포 전 확인: 요청에 지시문 블록과 캐싱 표시가 들어가는지, 다시 쓰기의 첫 블록이 처음 작성과 같은지, 사용량이 작업 기록의 받아들인·거부된 줄과 로그에 남는지를 테스트로 확인했습니다(테스트 지도 `docs/test-map/briefing.md`의 Claude 호출·작업 기록 행). 실제 서비스 흐름으로 급변동 작업 하나를 돌려, 처음 두 호출 뒤의 호출이 모두 캐시를 읽는 것을 작업 기록으로 확인했습니다.
- 판정 기준과 결과: 이슈 #48의 "시도 1" 댓글. 판정이 나면 여기에 요약합니다.

## 배운 점

- 구조화 출력의 응답 스키마도 캐시되는 앞부분에 들고 지시문보다 앞에 놓입니다. 같은 지시문을 쓰더라도 호출마다 스키마가 다르면 캐시를 나누지 못하므로, 캐시를 나눌 호출끼리는 스키마까지 같게 둬야 합니다.
- 공통 지시문에 호출별 덧붙임을 이어 붙이면 앞부분이 달라집니다. 덧붙임은 별도 블록으로 뒤에 두고 표시는 공통 부분 끝에 둡니다.
- 캐시 효과는 "얼마나 자주 부르나"보다 "같은 앞부분을 몇 분 안에 몇 번 부르나"로 정해집니다. 드물게 일어나는 작업도 그 안에서 여러 번 부르면 이득입니다.
