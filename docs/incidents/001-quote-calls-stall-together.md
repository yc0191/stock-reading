# 001. 시세 조회가 한꺼번에 10초씩 멈춤

- 상태: 진행 중(시도 1) - 조치는 develop에 들어갔고, 운영 배포 뒤 장중 2일로 판정합니다
- 기록일: 2026-11-13
- 관련: 이슈 #45, PR #47

## 증상

운영 첫 장중에 시세를 장중 시간의 절반가량 받지 못했습니다.

- 시세 조회의 시간 초과가 모두 정확히 설정한 제한(10초)에서 끊겼습니다.
- 시간 초과가 난 회차의 약 98%에서 그 회차의 조회 전부가 동시에 멈췄습니다.
- 수집기는 앞 회차가 끝나야 다음 회차를 돌리므로, 멈출 때마다 이어지는 1초 회차 9개를 건너뛰었습니다.
- 시간대와 상관없이 장중 내내 고르게 나왔고, 로컬 개발 환경에서는 같은 동시 조회가 회차당 1초 안에 끝났습니다.

## 조사

- **모두 제한 시간에서 끊김:** 응답이 늦게 온 것이 아니라 오지 않았습니다. 상대 서버가 느린 경우라면 끊기는 시각이 흩어져야 합니다.
- **회차 전체가 동시에 멈춤:** 종목 하나의 문제가 아니라 조회들이 함께 쓰는 무언가의 문제입니다. 함께 쓰는 것은 앱 전체 호출 상한과 HTTP 클라이언트 둘입니다. 호출 상한에 걸린 조회는 시간 초과가 아니라 건너뜀으로 따로 기록되므로 HTTP 클라이언트 쪽으로 좁혔습니다.
- **HTTP 버전:** Java 기본 `HttpClient`는 버전을 지정하지 않으면 상대가 받을 때 HTTP/2를 씁니다. 상대 서버가 TLS 인사(ALPN)에서 HTTP/2(`h2`)를 고르는 것을 확인했습니다(시세 API 호출 없이 TLS 인사만). HTTP/2는 동시 요청을 연결 하나에 함께 실어 보냅니다.
- **로컬에서는 안 남:** 코드 로직이 아니라 운영 서버에서 시세 제공자까지의 경로 차이로 봤습니다. 운영은 경로가 길어 연결이 멈추는 일이 잦고, 로컬은 짧아 드러나지 않은 것으로 봅니다.

## 원인 (추정)

회차의 조회 전부가 HTTP/2 연결 하나 위에 있었고, 그 연결이 멈추자 모두 시간 제한까지 기다렸습니다. 연결이 왜 멈추는지(경로의 손실인지 상대 서버 쪽인지)는 미확인입니다.

## 고친 것과 고르지 않은 대안

| 선택지 | 판단 |
|---|---|
| **HTTP/1.1로 고정 (고름)** | 동시 조회마다 연결을 따로 써서, 연결 하나가 멈춰도 그 조회 하나만 늦습니다 |
| HTTP/2 유지, 시간 제한만 줄이기 | 멈출 때마다 회차 전체를 잃는 구조가 그대로 남습니다 |
| HTTP/3 (QUIC) | 상대 서버의 지원을 확인하지 않았고, Java 21 기본 `HttpClient`에 없어 외부 라이브러리가 필요합니다. 연결 자체가 멈춘 경우에는 HTTP/3도 그 연결 위의 요청이 함께 멈추고, 중간 방화벽이 UDP를 막기도 합니다. Java 버전을 올릴 때 다시 봅니다 |

시간 제한도 함께 줄였습니다. 원인이 다른 데 있더라도 멈춤 한 번에 잃는 회차가 줄어듭니다.

- 현재가 조회의 응답 대기: 10초 → 2초. 1초마다 부르므로 오래 기다릴 이유가 없습니다.
- 연결 맺기: 2초. HTTP 클라이언트 하나를 같이 쓰므로 토큰 발급과 그 밖의 조회에도 같이 걸립니다.
- 토큰 발급과 그 밖의 조회(일봉, 시장종합 등)의 응답 대기: 10초 그대로. 하루 몇 번 부르는 조회라 짧게 끊을 이유가 없습니다.

감수하는 점: 동시 조회만큼 연결 수가 늘어납니다(호출 상한이 동시 조회 수를 묶습니다). 운영 서버에서 연결 맺기가 2초를 넘으면 토큰 발급도 실패합니다.

## 시도와 결과

### 시도 1: HTTP/1.1 고정과 시세 시간 제한 단축 (PR #47)

- 가설: 회차의 조회가 HTTP/2 연결 하나를 같이 써서, 그 연결이 멈추면 함께 멈춘다.
- 배포 전 확인: HTTP/1.1로 요청하는지, 현재가만 짧은 제한에서 시간 초과(`TIMEOUT`)로 끊기고 토큰·기타 조회는 같은 지연에도 끊기지 않는지, 클라이언트의 연결 맺기 제한 값을 테스트로 확인했습니다(`BrokerClientTimeoutTest`). 실제 시세 서버에도 토큰·현재가·기타 조회를 한 번씩 불러 HTTP/1.1로 정상 응답을 받았습니다.
- 판정 기준과 결과: 이슈 #45의 "시도 1" 댓글. 판정이 나면 여기에 요약합니다.

## 배운 점

- HTTP/2를 기본으로 쓰는 클라이언트는 동시 요청을 연결 하나로 묶습니다. 보통은 이득이지만, 연결이 멈추면 실패가 요청 하나가 아니라 묶인 요청 전체로 번집니다. 주기적으로 같은 서버를 동시에 부르는 작업은 실패 범위까지 보고 버전을 정해야 합니다.
- "모두 정확히 제한 시간에서 끊김"과 "회차 전체가 동시에" 같은 실패의 모양이, 개별 오류 메시지보다 원인 범위를 더 빨리 좁혔습니다.
- 주기 작업의 시간 제한은 주기에 맞춰 잡아야 합니다. 주기보다 훨씬 길면 한 번 멈출 때 이어지는 회차를 밀어냅니다.
