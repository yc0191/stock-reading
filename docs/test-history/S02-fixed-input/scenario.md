# S02 고정 입력으로 처리 시간 비교: 사양

같은 입력으로 반복해서 돌려, 코드나 설정을 바꾸기 전후의 처리 시간 차이를 비교합니다. 실제 검색 API 대신 가짜 검색 서버(`scripts/fake-news-search.py`)를 써서 실행 사이에 달라지는 값이 우리 코드와 환경뿐이게 합니다.

## 사양
- **구성**: 로컬 격리 Postgres와 Kafka, collector와 news 서비스(로컬 프로세스), 가짜 검색 서버. 스케줄은 끄고 틱을 수동으로 보냅니다(`scripts/publish-tick.sh collect-news`).
- **입력**: 검색어 31개, 검색어마다 응답 20건이 항상 같은 구성입니다. 필터 통과·서로 다른 기사 14, 주소 변형(`www.`, `utm_`) 2, 24시간 지난 기사 1, 1시간 넘게 미래인 기사 1, 검색어와 무관한 기사 2.
- **한 번의 반복**: 서비스 시작 → 소비자 lag 0 확인 → 테이블 비움 → 틱 5번(완료 확인 후 다음 틱) → 최종 상태 조회. 반복 사이에는 서비스를 종료하고 다시 시작합니다.
- **측정**: 수집 시간(가짜 서버가 틱의 첫 요청을 받은 시각 → collector의 `sent N news.collected events` 로그), 저장 시간(그 로그 → 같은 틱의 마지막 `news stored` 로그), 합계. 저장·합계는 첫 틱만 의미가 있습니다.
- **기대값**: 호출 31(5틱 155), 필터 통과 496·오래됨 31·미래 31·불일치 62(틱마다), 첫 틱 발행 434, 이후 틱 발행 0과 이미 발행 434, 저장 434.
- **합격 기준**: 5틱 완료, 건수 일치, 오류·`failed_event`·`article_key` 중복·lag가 모두 0.
- **회귀 판정**: 첫 틱 합계의 중앙값이 기준보다 20% 넘게 늘면 회귀. 반복 간 차이가 10%를 넘으면 불안정으로 표시합니다. 2~5번째 틱의 수집 시간은 수십 ms라 참고용입니다.
