# S02 고정 입력으로 처리 시간 비교: 결과

사양은 [scenario.md](scenario.md)에 있습니다.

## 환경 (R001, R007 공통)
같은 기기에서 측정했습니다. JDK 21, `pgvector/pgvector:0.8.7-pg17-trixie`, `apache/kafka:4.2.2`. 서비스는 커밋 `186417e` 기준(R007은 호출 간격 설정을 추가한 미커밋 상태, 간격은 0).


## 결과

### 건수 (모든 반복이 같음)
호출 155, 필터 496/31/31/62, 첫 틱 발행 434, 이후 발행 0·이미 발행 434, `news_article` 434, `news_article_symbol` 434, `article_key` 중복 0, `failed_event` 0, lag 0, WARN/ERROR 0.

- 2~5번째 틱의 수집 시간(발행 0건 경로)은 두 실행 모두 33~67ms입니다.


## 사건
- R001: 처음 두 번의 시도에서 시간 측정 기준(틱 발행 완료 시각)이 collector 완료보다 늦어 시간이 음수로 나왔습니다. 가짜 서버에 호출 시각 기록(`/__calls`)을 추가해 기준을 바꾸고 처음부터 다시 돌렸습니다(건수는 같았음). 시험 도구 변경이고 서비스 코드는 그대로입니다.
- R007: 1회차에서 저장 기사가 952건으로 나왔습니다. 앞선 탐색이 쌓아 둔 `news.collected` 이벤트를 news가 먼저 처리해 섞인 것입니다. 그 반복을 버리고, 시작 전 lag 0을 기다리도록 도구를 고친 뒤 다시 실행했습니다. 서비스 코드의 문제가 아닙니다.


## 한계
- 같은 기사가 서로 다른 검색어로 오는 경우는 이 입력에 없습니다(단위 테스트가 확인).
- 응답 시간이 0인 가짜 서버라 외부 API 지연은 반영하지 않습니다.
