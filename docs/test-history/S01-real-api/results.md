# S01 실제 API로 반복 수집: 결과

사양은 [scenario.md](scenario.md), 호출 간격 설정은 [call-interval.md](call-interval.md)에 있습니다.

## 결과 (R008, 호출 간격 60ms)
유효한 반복은 1회차와 3회차입니다. 2회차는 사건 참고.

| 반복 | 틱 | 수집(ms) | 저장(ms) | 필터 통과/오래됨/미래/불일치 | 발행 / 이미 발행 |
|---|---|---|---|---|---|
| 1 | 1 | 4,189 | 328 | 418/137/0/65 | 311 / 0 |
| | 2 | 4,629 | 131 | 418/137/0/65 | 89 / 232 |
| | 3 | 4,016 | 136 | 418/136/0/66 | 71 / 250 |
| 3 | 1 | 4,349 | 342 | 419/136/0/65 | 323 / 0 |
| | 2 | 4,588 | 109 | 420/135/0/65 | 76 / 242 |
| | 3 | 4,060 | 62 | 419/134/0/67 | 56 / 268 |

| 최종 상태 | 1회차 | 3회차 |
|---|---|---|
| 429 / WARN·ERROR | 0 / 0 | 0 / 0 |
| `news_article` / `news_article_symbol` | 426 / 499 | 431 / 488 |
| `article_key` 중복 / `failed_event` / lag | 0 / 0 / 0 | 0 / 0 / 0 |

- 합격 기준 6개를 두 반복 모두 충족했습니다. 틱은 15분 간격(±1초)으로 나갔고, 첫 틱에서 311~323건이 들어온 뒤 새로 올라온 기사 56~89건만 발행됐습니다(이미 발행한 기사는 다시 발행하지 않음).
- 연결 행이 기사보다 많은 것은 기사 한 건이 여러 종목에 연결되기 때문입니다.
- **계획한 3회 중 2회만 완료**했습니다.


## 관찰 (원인 미확인)
이후 틱에서 발행한 이벤트 일부를 news가 "이미 있는 기사에 합침"으로 처리했습니다(1회차 471건 중 45, 3회차 455건 중 24; 첫 틱은 0). 중복 저장은 없고 종목 연결도 합쳐져 데이터는 정상입니다. collector는 새 주소로 보고 news는 같은 기사로 본 것이라, 두 서비스의 주소 정규화 규칙이 완전히 같지 않은 것으로 보입니다. 영향은 불필요한 이벤트가 틱당 수십 건 더 나가는 정도입니다.


## 사건
- **R002**: 429로 중단했고, 경위와 해결은 [call-interval.md](call-interval.md)에 있습니다.
- **R008 2회차**: 기기가 절전에 들어가 뉴스 틱이 2번만 나가고 시계가 건너뛰어(news WARN `clock leap` 2건) 무효로 처리했습니다. 서비스 코드의 문제가 아닙니다. 재실행은 환경 조건으로 약 2분 만에 중단했고 결과는 없습니다.


## 한계
