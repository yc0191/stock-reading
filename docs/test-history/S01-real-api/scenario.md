# S01 실제 API로 반복 수집: 사양

실제 뉴스 검색 API로 검색어 31개를 15분 간격으로 반복 수집할 때 **에러 없이 계속 도는지**와 그때의 상태를 기록합니다. 실제 API는 응답 속도와 기사 양이 매번 달라서 이 시나리오의 실행끼리 숫자를 직접 비교하지 않습니다. 개선 전후 비교는 [S02](../S02-fixed-input/scenario.md)에서 합니다.

## 사양
- **구성**: 로컬 격리 Postgres와 Kafka, collector와 news 서비스. collector 스케줄을 켜 뉴스 틱이 15분마다 나가게 합니다(시세용 `collect` 틱도 30초마다 같이 나가며 오류를 내지 않음).
- **고정**: 검색어 31개, 요청 건수 20, 뉴스 틱 15분(첫 틱은 시작 직후), 한 반복 약 32분(틱 3번), 반복 3회, 반복마다 서비스를 새로 시작.
- **측정**: 틱 발행 시각, 수집 시간(틱 발행 로그 → collector 발행 완료 로그), 저장 시간(발행 완료 → 같은 틱의 마지막 저장 로그), 필터 결과, 발행·이미 발행 건수, 저장 행 수, 중복·`failed_event`·lag, WARN/ERROR 개수. 수집·저장 시간은 외부 API 영향이 커서 참고용입니다.
- **합격 기준**: ① 틱 3번이 모두 발행됨 ② 뉴스 경로 오류(`news query failed` 등) 0 ③ `failed_event` 0 ④ `article_key` 중복 0 ⑤ 마지막 lag 0 ⑥ 서비스가 재시작 없이 끝까지 동작.
- **주의**: 실행 중 기기가 절전에 들어가면 서비스가 멈춰 틱이 빠집니다. 절전을 막은 상태로 실행합니다. 앞선 실행이 남긴 이벤트가 섞이지 않게, 시작 후 lag 0을 확인하고 테이블을 비웁니다.
