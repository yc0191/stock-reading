# 호출 간격 설정과 기본값 결정

S01 R002에서 나온 429를 풀기 위해 추가한 설정과, 기본값을 정한 탐색(R003~R006)의 기록입니다.

## 변경
- **계기(R002)**: 검색어 31개를 호출 사이 대기 없이 연달아 호출(약 50ms 간격)하자 첫 틱에서 31번 중 9~16번이 `HTTP 429`로 거절됐습니다. 429가 나도 재시도 없이 그 검색어를 건너뛰어, 해당 틱에서 그 검색어의 기사가 빠졌습니다(저장된 기사에는 중복·오염 없음). 3번 시도 모두 같았습니다.
- **내용**: `collector.news-search.call-interval-ms`(기본 60) 추가. 검색어를 연달아 호출할 때 호출 사이에 이만큼 쉽니다. 31개면 틱당 약 1.8초가 늘어납니다.
- **기본값을 정한 근거**: 아래 간격 탐색 표.


## 호출 간격 탐색 (R003~R006)
실제 API에 검색어 31개로 틱 하나만 보내고, 간격을 바꿔 가며 429 개수를 셌습니다(실행 70번, 호출 2,170회).

| 간격(ms) | 실행 수 | 429가 난 실행 | 429 합계(건) |
|---|---|---|---|
| 0 | 6 | 6 | 90 |
| 10 | 3 | 3 | 29 |
| 20 | 3 | 3 | 14 |
| 30 | 3 | 3 | 12 |
| 40 | 5 | 4 | 11 |
| 50 | 11 | 1 | 1 |
| 60 | 6 | 0 | 0 |
| 70 | 6 | 0 | 0 |
| 80 | 6 | 0 | 0 |
| 90 | 6 | 0 | 0 |
| 100 | 6 | 0 | 0 |
| 150 / 200 / 300 | 각 3 | 0 | 0 |

- 간격이 길수록 거절이 서서히 줄었습니다(칼로 자른 경계가 아님). 429가 아닌 실패는 없었습니다.
- **60ms 선택**: 규칙("6번 모두 429가 0건인 가장 짧은 값", 결과를 보기 전에 고정)에 따라 정했습니다. 처음 도입한 잠정값은 200ms였습니다.
- 한계: 60ms는 6번(호출 186회) 표본이라 완전히 안전하다는 증거는 아닙니다. 공식 호출 한도는 확인하지 못했습니다(미확인).
